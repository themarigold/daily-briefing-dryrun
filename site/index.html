Pick up where you left off.

daily-briefing is a morning briefing for developers who work with AI coding assistants. It reads your local git history and tells you where you left off, what you did, and what to do next, written by the AI you already use and ready when you first sit down.

A desktop app for macOS and Linux, and a command-line tool for macOS, Linux and (experimentally) Windows. No account, no server: it runs on your machine.

Privacy

daily-briefing is local-first and has no telemetry of its own: no analytics, no usage or crash reporting, no account, and no server of its own. It reaches the network in seven places, and no others. The AI provider you choose: the prompt, built from your commit subjects, short hashes and dates, the names of changed and uncommitted files, repository and branch names, and stash messages, goes to that provider under its terms, through the AI tool you configure (provider.cli) or as one HTTP(S) request per attempt to the API endpoint you set (provider.api), which is encrypted only if that endpoint is https:// (a plain http:// endpoint that is not on your own machine sends the prompt and your API key unencrypted). Point it at a local model and the prompt never leaves your machine. The calendar links you add, only if you turn the calendar on: each run sends one HTTPS GET per private calendar link you added, to that link's own host, following at most three redirects and only within the same domain. The desktop app's live read fetches every link the same way each time it reads: when you move onto the calendar slide or the last slide and, while either is shown, when the window regains focus, when you turn the calendar on, when a meeting card or Join button finds the last read out of date, and every five minutes. Nothing about you or your repositories is sent; the link's address itself is the secret that lets the host answer. AI summaries are off unless you turn them on. With them on, a delivered briefing on a day that is not quiet makes a second AI call, if the page has at least one project card. Generating the same day's briefing again can make another when it is delivered. It goes to the same provider entry that wrote the briefing, with one try and no fallback. If it is your key source, your apiKeyCommand runs again for this call. An attempt is locked when it cannot act on what it reads. Every attempt leaves out the computer's name, the page's warning and notice lines and the line that names the provider. A locked attempt gets the saved page. An unlocked attempt after an unlocked morning gets the saved page with the calendar section's body replaced by schedule shape: times, busy blocks and attendee counts, with no event title, location or attendee names. The calendar section also carries today's date, the current time and your time zone and, when a calendar source could not be read fully, that source's id, which can hold a name, as in work-alice. An unlocked attempt after a locked morning makes no call. If you turned transcripts on, the call includes the page's — you wrote quotes from your sessions, up to 600 characters each. No call is made when AI summaries are off or on a quiet day. No live details are added. The result shows only on the desktop app's slides. The call is still made with the slides off or with no desktop app, because the engine cannot read that app setting. The result is stored at <state>/briefings/<date>.<hash>.<version>.summary.json. It stays after you turn AI summaries off, and other dates' files are not pruned; it goes with the briefing archive when Uninstall removes the engine's data. A locked attempt's text may name a meeting. AI summaries are not available on Windows yet. No summary call is made on Windows. A connectivity check before it generates, and, on macOS, each time the desktop app opens: a TCP connection to the hosts in networkProbeHosts (by default 1.1.1.1 and 8.8.8.8, or your API endpoint), opened and closed with no data sent, which you can turn off. GitHub, only if you turn on the update check or ask for one: a single anonymous request to api.github.com for the latest release, carrying the version number, and after the first answer GitHub's own cache tag, and nothing about you or your code. GitHub again, when you press an Open on GitHub button in the desktop app (Open PR, Open branch, Compare or a commit's arrow): your browser opens that page, so the owner, repository and branch names in its address, and its PR number or commit ID, go to github.com through your browser; the GitHub links switch turns these off. Your repository's own remote, only in a partial clone (one made with --filter, or by scalar clone): the tool never runs git fetch, pull or push, but when it reads such a repository's history, git itself downloads the file contents it is missing from that remote, with your usual git credentials. A normal clone never does this. Otherwise git only reads your local repositories. It can also start helper programs your own git configuration names (a diff driver, an fsmonitor hook, or a filter), and what those contact is up to them. And the Bun runtime the engine is built with, only if Bun itself crashes: on macOS and Windows it can send Bun's team a crash trace (Bun's version, your platform, an internal stack trace, the crash reason and which Bun features were used; no source code or personal information, per Bun) to bun.report. The desktop app and the macOS schedule turn this off; for a run you start from a terminal, or the experimental Windows schedule, set DO_NOT_TRACK=1 to turn it off. The full privacy notes
