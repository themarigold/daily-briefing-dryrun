# Self-hosted scheduled delivery (Linux)

Running the briefing on an always-on box — a home server, a VPS, a container that stays up — uses
the same `schedule install` as everywhere else. There is **no hosted backend and nothing new to
build**: a systemd user timer plus, if you want to be told about it, a `notify.command` that pushes
to an endpoint you already own.

> ## ⚠ Read this caveat first — it decides whether self-hosting is useful to you at all
>
> **A self-hosted briefing briefs THAT MACHINE's repos.**
>
> `machineScope` is per-machine by design: the engine reads the git history that exists on the box it
> runs on. Self-hosting buys **delivery reliability for a machine whose repos are the ones you care
> about** — a server you actually commit on, or one where you keep clones you work in over SSH. It
> buys **nothing at all** for the local work on your laptop, because that history is not on the
> server. If your commits live on the laptop, schedule it on the laptop.
>
> This is a property of the product, not a limitation of the Linux leg.

> **Evidence status.** The systemd unit files are generated by the same tested generator as the macOS
> plist, and are linted by `systemd-analyze verify` when that binary is present. As of this writing
> **no end-to-end run on a real Linux machine has been recorded in this repo.** Treat the Linux leg as
> "generates, lints, unexercised" until that changes.

## 1. Install

```sh
daily-briefing init                     # writes ~/.config/daily-briefing/config.json
daily-briefing schedule install         # writes + enables the user timer
```

`schedule install` copies the engine to `~/.local/share/daily-briefing/bin/daily-briefing` and points
the unit at **that copy**, never at the file you downloaded. That is not tidiness: an AppImage's
interior path is an ephemeral `/tmp/.mount_XXXX/…` recreated on every launch, so a unit pointing
inside the mount works exactly once. The installer refuses to write a unit that references a mount
path.

It writes two files into `~/.config/systemd/user/`:

| File | What it does |
| --- | --- |
| `daily-briefing.service` | `Type=oneshot`, absolute `ExecStart=<managed copy> run` |
| `daily-briefing.timer` | `OnBootSec=2min`, `OnUnitActiveSec=10min`, `OnCalendar` at your morning floor, `Persistent=true` |

Two triggers, for the same reason macOS gets two: the monotonic arm polls, and the calendar arm
fires once at the floor and — thanks to `Persistent=true`, which systemd only honours for calendar
timers — **catches up a fire the machine missed while it was down**. The once-a-day marker dedupes
the second fire, so the cost is one no-op run per day.

## 2. ⚠ Lingering — the difference between working and silently never firing

**systemd user units do not run while you are logged out.** On a headless box that is every minute of
every day, so the timer would simply never fire and nothing would tell you.

`schedule install` detects this and prints the exact command. To enable it:

```sh
loginctl enable-linger "$USER"          # or: daily-briefing schedule install --enable-linger
```

`daily-briefing schedule status` reports `linger: enabled | disabled | unknown`. Check it once after
install; `unknown` means the probe could not answer and deserves a look, because this is exactly the
setting whose failure mode is silence.

## 3. Getting told about it — `notify.command`

There is no desktop on a server, so `notify: "auto"` has nothing to talk to. Use the explicit form,
which is an **argv array, never a shell string**:

```json
{
  "morningTime": "07:20",
  "notify": {
    "command": ["curl", "-fsS", "-X", "POST", "-d", "{body}", "https://ntfy.sh/your-private-topic"]
  }
}
```

`{title}`, `{body}` and `{path}` are substituted **inside individual argv elements**. A value
containing a space or a semicolon stays one argument — nothing is word-split and no shell is
involved.

The body is a **fixed template**: `Your briefing for <date> is ready — <path>`. It never contains
briefing text, commit subjects, branch names or filenames from your repos. That is deliberate and not
configurable: those strings are attacker-influenced in the general case, and a fixed body removes the
whole class rather than sanitizing around it.

The notification is sent **after** the day is marked done, and every failure is swallowed — a missing
`curl`, a dead endpoint or a hung request cannot cost you a briefing.

## 4. Checking it works

```sh
daily-briefing schedule status          # registered? owner? ticks today vs expected? last delivery?
daily-briefing schedule verify          # kick the trigger through systemd and report what happened
daily-briefing doctor --json            # repos readable? provider present? network reachable?
systemctl --user list-timers daily-briefing.timer
journalctl --user -u daily-briefing.service -n 50
```

`schedule status`'s **ticks today vs expected** is the diagnostic that matters: a low tick count means
the *timer* is not firing (check lingering first), while a healthy count with no delivery means the
run is reaching the engine and declining — and `last skip` then says why.

## 5. Removing it

```sh
daily-briefing schedule uninstall       # disables + deletes the units and the ownership record
```

This removes the **schedule**, not the tool: the managed copy of the engine is left where it is.
Delete `~/.local/share/daily-briefing` and `~/.local/state/daily-briefing` by hand if you want the
binary and its state gone too.

## Notes

- **Ownership.** `<state>/schedule.json` records who installed the trigger. If the desktop app
  installed it, a CLI `schedule install` refuses (exit 2) rather than silently replacing a
  configuration you set up on purpose; `--take-over` claims it deliberately. Exit codes are
  `0` ours · `1` nothing found · `2` a foreign owner holds it · `3` error.
- **Config and state paths** follow XDG on Linux: `~/.config/daily-briefing/config.json` and
  `~/.local/state/daily-briefing/`. `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_DATA_HOME` are all
  respected, and `DAILY_BRIEFING_STATE_DIR` overrides the state dir outright.
- **No provider on the box?** Set `networkProbeHosts: []` if it is offline, and point
  `provider.cli` at whatever you do have. The engine never phones home on its own.
